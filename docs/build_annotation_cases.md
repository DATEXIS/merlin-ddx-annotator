# Create a new V1–V4 reasoning annotation study

This is a new workflow, not the recovered historical pair builder. The historical
DDx and rationale-audit studies, their exact rubrics and analysis code remain
available. New studies compare complete **raw stage outputs**, not
reference-corrected SFT targets or necessarily individual diagnosis/code rationales.

## Input sources

The raw MERLIN generation table is produced by
[MERLIN postprocessing](https://github.com/DATEXIS/merlin/blob/main/src/postprocessing/merge_gen_data.py):
`data/results/gen_data/combined.pq`. Required columns are
`hadm_id`, `gen_model`, `split`, `Chief Complaint`, `admission_note`
and `v{1,2,3,4}_json`, `v{1,2,3,4}_text`, `v{1,2,3,4}_score`
for selected stages. V3/V4 construction outputs additionally require `labs`
because those upstream construction prompts use laboratory results.
The parser reads raw JSON and raw response text without reference alignment;
it skips missing or unparseable stage outputs. It does not interpret a verifier
score as ground truth or infer acceptance from it. Do not feed the corrected
instruction dataset produced by the SFT postprocessor.

A separate comparator can be provided as normalized JSONL, one row per
admission/stage/model. Required fields (all strings):
`hadm_id`, `stage` (V1–V4), `model`, `trace_id`, `split`, `chief_complaint`, `admission_note`, `clinical_context`, `target`, `reason`.
The optional fields `verifier_score` and `verifier_accepted` are kept as
private metadata. `clinical_context` contains additional evidence, not
arm-specific model predictions; it must be nonempty for V3. Use an explicit
empty string when a stage has no additional evidence. A comparison between
different generation methods must provide its actual outputs; a rejected loop
output is not a zero-shot response. No outputs are generated by this tool.

## Build and run

Install the analysis extras and build the frontend as in the main README.
Example: compare two models in the same raw generation table, over all four stages.

```bash
uv run python scripts/build_annotation_cases.py \
  --left /authorized/data/combined.pq --left-model Qwen3-32B \
  --right /authorized/data/combined.pq --right-model medgemma-27b-it \
  --split test --stages V1 V2 V3 V4 --seed 42 --n 20 \
  --out /authorized/studies/study01

uv run python scripts/run_demo.py \
  --data-root /authorized/studies/study01/annotation_inputs
```

Open the local server. Do **not** use `--reset` or `--with-ratings` on real studies.

The importer requires unique records per admission/stage within each arm,
matches the arms by admission and stage, checks common evidence, and samples
admissions with all requested stages available. It samples uniformly from the
eligible complete-case population (not a stratified or representative design).
`--complaints` restricts the complaint set; `--raters` controls the number
of configured raters. A fixed seed and identical inputs reproduce sampling and
A/B assignment. Separate comparison conditions are never substituted silently.

The study-specific opaque identifiers also separate browser storage keys from
other studies. The annotation input directory holds only the blinded case
material and generic rater list. The sibling `private_analysis/` directory
contains the allocation key, source artifact digests, original admission/trace
identifiers, model identity and verifier metadata. Do not mount or serve it.
Opaque identifiers do not anonymize clinical texts. Original text may itself
reveal a model or experimental condition; review this risk before a study.

## Stage-specific questions

All new studies use the same Yes/No/Unclear response vocabulary and common
factual-grounding question. Q2 changes with the task:

| Stage | Q2 focus |
|---|---|
| V1 | Correct and complete manifestation classification, including explicit absence and unmentioned findings |
| V2 | Clinical support for the differential diagnosis ranking |
| V3 | Clinical support for the updated ranking given available labs |
| V4 | Clinical support for the predicted ICD diagnoses and their specificity |

These are proposed new-study rubrics, **not clinician-validated instruments**.
Review them with clinicians before collecting data. The historical V2/V4
single-target rubric is unchanged. Stage-output annotations are not directly
comparable to historical single-target annotations. Full outputs are displayed
as supplied, without adding code descriptions or reference answers.
The additional clinical context is shown only on the relevant stage panel.
When stages appear together on one admission, raters can see the other stage
panels; use separate single-stage studies if cross-stage evidence exposure
would affect the experimental question.

## Export and analyze

After completing and freezing ratings locally:

```bash
uv run python scripts/export_annotations.py \
  --study /authorized/studies/study01 \
  --out /authorized/studies/study01/private_export

uv run python scripts/analyze_annotation_study.py \
  --export /authorized/studies/study01/private_export \
  --out /authorized/studies/study01/private_analysis/summary.json
```

The exporter validates saved responses against the case schema and allocation
key, maps A/B back to left/right, and writes aggregate Q1, Q2 and joint-composite
vote counts per trace plus pair-level preferences. It preserves missing votes
and excludes comments and individual rater identities. Trace identity is
qualified by the source artifact digest. By default every assigned rater must
complete all pairs. An explicit `--allow-incomplete` enables partial export;
the general statistical analysis rejects missing Q1/Q2/composite votes.

The analysis reports rates by stage/condition, paired admission-cluster
percentile bootstrap intervals and descriptive verifier-score associations
with trace-level mean composite validity. It counts Unclear as non-Yes for
the primary rate, retains the original distributions in the export, and does
not calculate an interval from a single admission. It does not replace the
historical audit analysis or report new-study inter-rater kappa yet.
The pairing/preferences export can be used for additional analyses.

## Data handling and scope

This is a trusted, local research interface, not an authenticated multi-user
annotation service. The current backend does not enforce rater identity or
independence. Use separate controlled environments or a properly authorized
access-control layer before a multi-rater remote deployment; do not expose the
demo server publicly. Do not commit patient-derived inputs, identifiers,
allocation keys, ratings or exports. Work in authorized storage outside the
repository. No external model calls or GPU jobs are used. The original
dataset-to-DDx case importer, enforced independent mode, and clinical validation
of these new rubrics are separate follow-up tasks.
